## New findings

### C14 — should-fix — `src/http/limits.js:132-135` (the untracked path), `:160` (`untracked()`), `src/http/server.js:128`

Past the table's bound, the two failure budgets are off for every key not in the table, and nothing reports it.

- **Failure scenario**: 10,000 keys each make one call in a minute, about 170 requests a second; the calls need not fail. For the rest of the window any other address sends dead cookies or junk uploads without limit, each costing one store read or one RSA check. On main, such an address was served 30 and 60.
- **Cost to the attacker**: 10,000 /64s fit in one IPv6 /48. As in the previous report, I could not check whether the hoster forwards IPv6 client addresses; otherwise it needs 10,000 IPv4 addresses.
- **What the code's comment says**: it states the trade and argues a holder of 10,000 keys was already unbounded. That holds with bursts, but the filling calls can be cheap and non-failing, and the unbounded caller can be anyone.
- **No visibility**: `untracked()` and `tracked` are read nowhere in `src/`. No log line or health field says the budgets are off.
- **Reproduction** (NAS):
  - Real sockets, after the C11 flood: `one address past the bound, 5,000 dead cookies: {"401":5000} store transactions: 5000`.
  - Same for uploads with a well-formed token and a wrong signature: `{"401":5000} RSA checks: 5000`.
  - Control, an address of the table: `{"429":200} store transactions: 0`.
  - Unit, table filled by 10,000 keys that did not fail, then one more key fails 100,000 times: old `signedOut` served 30, old `machine` 60; new served 100,000 on both.
  - One /48: `10,000 /64s, one call each, no failure: table size 10000; the next /64 of the same /48: tracked = false`.
- **Suggested fix**: at least log once a window and expose the untracked count in `/api/health`, so the probe can alert. To narrow it, add an aggregate budget one level up (IPv6 /48, IPv4 /24) with a larger allowance, so a single prefix cannot fill the table.

### C15 — should-fix — `.github/workflows/send.yml:94-161` (the send job), `:24` (header), `README.md:38-39`

The send job runs `node "$RUNNER_TEMP/send.mjs"` and installs no Node.js; only the check job has `actions/setup-node`.

- **Failure scenario**: a caller passes `runner: '["self-hosted","nas"]'` on a machine with no `node` on PATH, as the README allows ("Node.js 22 is installed by the workflow"). On a push to main the send step exits 127, the send job fails, and the run is red whatever `send-strict` says.
- **What the docs promise instead**: "the check runs and the run keeps runward's verdict, and the upload is reported not accepted".
- **Variant**: with a system Node.js older than 18, `fetch` is missing. Each attempt throws inside the `try`, and the summary says "service unavailable after 4 attempts" after about 40 s, which is wrong.
- **Not reproduced**: by reading only; no Actions run.
- **Suggested fix**: list Node.js 22 on PATH among the runner's needs in the README and the header. Or start the send step with a `command -v node` check that writes "not sent: no Node.js on this runner" to the summary and exits per `send-strict`. Adding `setup-node` to the send job would trip the guard's own rule (`scripts/check-workflows.mjs:69`).

### C16 — should-fix — `scripts/check-workflows.mjs:42-51`

The guard went from "the word `self-hosted` anywhere in a workflow" to "a `runs-on:` line that names it", and three spellings the main guard refused now pass.

- **Failure scenario**: a workflow of this public repository gets a self-hosted runner through one of these, and `check-workflows` exits 0 with "hosted runners only".
- **Reproduction** (NAS, planted on a copy of the workflows; each is refused on `ci.yml` by main's guard):

  - `runs-on: *own` with `x-own: &own [self-hosted, nas]` (alias): new guard PASSES.
  - A call to `send.yml` with `"runner": '["self-hosted"]'`, in flow or block style: new guard PASSES.
- **Never caught, before or now**: `runs-on:` with `group: own-machines`, and `runs-on: nas` (an own label without the word).
- **Controls that hold**: `[self-hosted, nas]` inline, the block list, and an unquoted `runner:` are refused.
- **Suggested fix**: keep the whole-file `self-hosted` test for every file but `send.yml`, and for `send.yml` apply it with comment lines removed. Match the keys with optional quotes. Refuse a `runs-on` whose value is not one of a closed list of hosted labels, which also covers groups, aliases and own labels.

### C13 — note — `scripts/migrate.mjs:129` (`DYNAMIC`, the `execute` rule)

The exemption for a trigger's `execute function f(` matches PL/pgSQL code where `function` or `procedure` is a variable or a parameter, followed by anything and an opening parenthesis.

- **Why it matters**: the header's "`execute` of a text, anywhere" is still broader than what is refused. `test/unit/migrations.test.js:162-163` covers `execute function;` and `execute function || ' …'`, not the parenthesised form.
- **Reproduction** (NAS, PostgreSQL 17.11; each gives `contracting() = null`, `planMigrations: planned`, and `public.victim GONE`):
  - `do $$ declare function text := 'dr'; begin execute function || ('op table public.victim'); end $$;`
  - `do $$ declare procedure text := 'dr' || 'op table public.victim'; begin execute procedure || (''); end $$;`
  - `create function public.g(function text) … as $$ begin execute function || (''); end $$; select public.g('drop table public.victim');`
  - `… begin execute function ::text||(''); end $$;`
- **Suggested fix**: apply the exemption only outside dollar-quoted bodies, or only in a statement that begins with `create [or replace] [constraint] trigger`. Inside a body, refuse every `execute`.
- **Outside this diff**: `alter table public.victim set schema attic;` gives `contracting() = null` and moves the table away, a rename in effect. `query_to_xml('drop table …')` passes the guard but the server refuses it ("DROP TABLE is not allowed in a non-volatile function").

### C17 — note — `src/application/operator.js:179-187` (`anchoredHead`, the equal-head case at `:183`)

An anchor taken after the restore and before the first replay is read as the head before the loss.

- **Failure scenario**: the operator anchors (head 8), restores (head 5), runs `--anchor` again by mistake, then replays. The permanent note says 0 entries lost although three were lost and their anchor is in the log.
- **Scope**: the logic is unchanged by this PR and main gives the same result. It is listed because it is the class C12 was about, and the existing test covers only an anchor taken after the first replay.
- **Reproduction** (NAS, memory store): with the second anchor, `lost={"from":null,"to":null,"count":0} headAfterRestore=5 headBefore=5`; control without it, `lost={"from":6,"to":8,"count":3}`.
- **Suggested fix**: when an anchor of an entry the journal no longer holds exists after `since`, prefer it over an anchor equal to the restored head. Or refuse `--anchor` when the latest anchor is ahead of the journal's head.
- **The previous report's hypothesis, now reproduced**: after a first replay (note `6..8`), the journal goes on to 7, is anchored, and the same backup is restored again. The note says `{"from":6,"to":7,"count":2}`. That is true of the second loss, but the journal no longer says anywhere that seq 8 existed. Recorded, not counted as a defect.

## Checked with no finding

- **Limiter memory**: 2,000,000 distinct /64s in one window leave the table at 10,000 keys, 1,990,000 untracked, and 1.6 MB of heap growth. `flying` holds tracked keys only.
- **Eviction abuse**: there is no eviction, so nothing to abuse; a key in the table keeps its counters for the window.
- **Per-request cost**: `addressKey` takes about 5.9 µs for an IPv6 address and 0.13 µs for an IPv4 one. Five hostile 16,000-character strings take 0.05 to 0.53 ms each, with no backtracking blow-up.
- **Key forms**: `::FFFF:1.2.3.4`, `0:0:0:0:0:ffff:102:304` and `[::ffff:1.2.3.4]:80` all key to `1.2.3.4`; a zone is dropped; upper-case hextets are normalised. `1.2.3.4:80` and `001.2.3.4` are their own keys, which only matters if the proxy writes them.
- **Settle paths**: an untracked failure counts for the instance only. A tracked call that settles after the window turned onto a full table counts for the instance only.
- **Public routes**: `rateLimiter` still shares `(overflow)` past the bound, but its global budgets (600 writes, 3,000 reads) are below 10,000, so the shared counter cannot be reached.
- **C12 reruns**: a third run repeats the first range and names it (`rerunOf=6`).
- **Migration guard, the rest**: `0001_floor.sql` hashes to the value in `DYNAMIC_READ`. A trigger's `execute function` and `grant` / `revoke execute on` pass. The refusal says "could contract" for the two dynamic kinds.
- **Send deadlines**: check 15, send 5, verdict 5 minutes. The send job's worst case is about 200 s (four attempts of 10 s token plus 30 s upload, and 40 s of waits), under its deadline.
- **`image-smoke.mjs`**: the token is read only from a 200 that parses and carries a string `value`; five tries, 3 s apart; `sleep` and `fail` exist; the CI job that runs it has a 20-minute deadline. The token request has no timeout of its own, so a hang ends at the job's deadline.
- **README**: the calling example grants `id-token: write` to the calling job and pins `send.yml` by commit.
