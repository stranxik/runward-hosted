## Findings

### C28 (should-fix): the comment and the runbook say the rights of `rw_app` and `rw_maint` are still checked at each deploy; no check reads their table rights

- **Where**: `infra/scaleway/main.tf:306-316` (the claim, line 314), `:331`, `:341`; `runward/runbook.md:158`; `runward/JOURNAL.md` ("`roles` and the isolation suite of each deploy check their rights").
- **What the two checks read**:
  - `scripts/roles.mjs:36-58`: role attributes and the database-level `connect`, `create`, `temporary`.
  - `scripts/isolation-deployed.mjs:14-30`: rows crossing between the two witnesses, one refused write, `rolbypassrls`, and the search path of the definer functions.
  - Neither reads a table privilege in the schema `rw`.
- **Failure scenario**: the level of `rw_app` is raised at the hoster (console or API) to `readwrite` or `all`. With `ignore_changes = [permission]`, no plan shows it. `roles` and `isolation` stay green, since row-level security still holds. `db/grants.sql` only grants (plus one `revoke truncate`), so the next `migrate` takes nothing back. The invariant "no DELETE anywhere" for the service role would then be gone with no signal.
- **Not verified**: whether the hoster's preset reaches tables of the schema `rw`. The provider's wording quoted in the file ("all objects, existing and new") suggests it does.
- **Before this change**: a plan showed that drift, among the constant `custom -> readonly` noise.
- **Suggested fix**: keep the `ignore_changes`, and add the missing check where the text says it is: compare, on the deployed base, the grants of `rw_app` and `rw_maint` (`information_schema.role_table_grants`, plus `has_schema_privilege` and `has_database_privilege` for `create`) with the grant lines of `db/schema.snapshot.txt`. `roles` runs as `rw_admin` at each deploy and can do it. Until then, reword the three places to say what is checked.

### C29 (should-fix, not verified): the smoke's premise about the hoster's router has not been observed

- **Where**: `scripts/smoke.mjs:34-58`; `.github/workflows/deploy.yml:107-108`; `runward/JOURNAL.md` ("Next: the author sets the repository variable").
- **The premise**: the router accepts a request whose TLS server name is `app.runward.dev` and whose `Host` is the container's default hostname, and routes it to the service. It is proven only against the local stand-in of `test/unit/smoke.test.js`, which routes by `Host` alone.
- **Failure scenario**: the router refuses or misroutes a request whose server name and `Host` differ (its own 421, or a 404). The smoke reports a fault on a healthy deploy, and the `rollback` job redeploys the previous digest. Every deploy then rolls back.
- **Direction of the error**: safe. It cannot pass with a broken guard, since only the app's JSON refusal passes.
- **What settles it**: one run by hand, before `RW_DEPLOY_ENABLED` is relied on, of the command runbook §7 gives: `RW_SERVICE_HOST=<default hostname> node scripts/smoke.mjs https://app.runward.dev <commit>`. I did not run it.
- **Suggested fix**: record that run's output in the JOURNAL. If the router refuses the mismatch, ask the default hostname as its own origin (server name and `Host` both the default hostname) instead of mixing the two.

### C31 (note): `RW_SERVICE_HOST` is taken on trust

- **Where**: `.github/workflows/deploy.yml:61-65`; `scripts/smoke.mjs:61-66`.
- **The gap**: the variable is compared with `$SERVICE` only. The same job reads the service's container at the hoster two steps later (`deploy.yml:67-73`) and could compare the variable with that container's own hostname. As written, a value that names another routed host answering the same refusal would pass.
- **Related**: the "never the origin's own" test is by exact string. The origin's host with a trailing dot is sent and passes (run S4: exit 0). The 421 is still the app's own, so nothing false is proven.
- **Suggested fix**: after the `before` step, refuse when the variable differs from the hostname the hoster reports for `vars.SCW_CONTAINER_ID`.
